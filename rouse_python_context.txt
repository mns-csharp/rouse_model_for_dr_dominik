OBJECTIVE
=========

Validate that the SURPASS-alpha coarse-grained (CG) polymer representation
abides by Rouse static and dynamic properties as published in:

  [REF-1] Kuriata, A., Gront, D. & Sikorski, A., CMST 22(4), 179-185 (2016)
  [REF-2] Rouse, P.E. Jr., J. Chem. Phys. 21(7), 1272-1280 (1953)

Specifically:
  (a) Prove compliance with all static and dynamic Rouse properties in [REF-1].
  (b) Determine which Rouse properties in [REF-2] ARE met by SURPASS-alpha.
  (c) Determine which Rouse properties in [REF-2] are NOT met by SURPASS-alpha.
  (d) Map how Rouse property compliance changes across a progression of
      increasing chain densities (phi), from dilute to dense regimes.
  (e) Produce publication-quality plots and structured data for all findings.

Key physical clarifications confirmed by Dr. Dominik Gront (30 Mar 2026):
  -- The excluded volume energy E is INFINITE. Any move violating excluded
     volume is ALWAYS rejected regardless of simulation temperature. This
     makes the system effectively athermal: temperature is irrelevant to the
     accept/reject decision because exp(-inf/kBT) = 0 for all finite T.
  -- Concentration (phi) is NOT fixed at a single value. A progression of
     increasing densities must be tested to map where and how Rouse behavior
     is fulfilled, weakened, or broken.

SYSTEM CAPABILITY QUERY (AT STARTUP):
  - Before any simulation begins, the framework MUST query the OS environment

      (a) Number of GPU devices attached to the system.
      (b) Number of CPU cores available.
  - This information is logged at startup for diagnostics and dispatch
    decisions. It does NOT override the user's --device choice.

EXECUTION POLICY TABLE:
  Given N = number of beads, with chain-length set N = {n_1, n_2, ..., n_k}:

  --device | --is_parallel | Behaviour
  ---------|---------------|----------------------------------------------------------
  cpu      | false         | RUN -- serial CPU, step_size = 1.
           |               | Baseline mode; safe for debugging / single-chain profiling.
  cpu      | true          | RUN -- parallel CPU, step_size > 1.
           |               | CPU thread-level parallelism. Each n_x simulation
           |               | distributed across available cores.
  gpu      | false         | WARN -- falls back to serial GPU execution.
           |               | Emits a warning and continues (useful for debugging or
           |               | profiling a single run). Pass --force to suppress warning.
  gpu      | true          | RUN -- parallel GPU, step_size > 1.
           |               | PyTorch tensors manage internal GPU scheduling; no
           |               | explicit single-chain threshold needed. For large n_x:
           |               | use batch processing / chunking / data streaming to stay
           |               | within VRAM limits. Dispatcher checks available VRAM
           |               | before assigning a batch.
  mixed    | false         | WARN -- falls back to CPU-only serial.
           |               | Warns and runs on CPU. Allows user to validate results
           |               | before committing to full mixed execution.
  mixed    | true          | RUN -- hybrid CPU+GPU, optimised dispatch.
           |               | CPU handles lightweight or memory-constrained chains;
           |               | GPU handles compute-heavy chains. Workload partitioning
           |               | is automatic based on n_x size and available VRAM.

SIMULATION DISTRIBUTION POLICY:
  Condition                        | Policy
  ---------------------------------|--------------------------------------------------
  Multiple GPU devices attached    | Distribute individual n_x simulations across
                                   | devices automatically at startup.
  A device completes early         | Reassign the next pending simulation to the idle
                                   | device. Completion defined by MC sweeps (not wall
                                   | time or convergence criterion).
  Large n_x / VRAM pressure        | Dispatcher uses batch processing, chunking, or
                                   | data streaming to avoid OOM. VRAM headroom
                                   | checked before each batch assignment.
  Single chain N = {n_1}           | No special handling needed. PyTorch tensor
                                   | scheduling manages GPU utilisation internally.

NOTE ON step_size VS is_parallel:
  These are independent parameters. step_size controls MC move granularity;
  is_parallel controls execution strategy. Validation checks each independently.
  A run may specify step_size > 1 with is_parallel=false for batched-but-serial
  execution, or step_size = 1 with is_parallel=true for parallel single-step runs.
